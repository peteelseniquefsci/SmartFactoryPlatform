## Context and current state

The Smart Factory department of First Sumiden Circuits Inc. (FSCI, electronics manufacturing, Philippines) runs a cascaded Balanced Scorecard for 2H FY2026 (October 2026 – March 2027) that today lives in 57 Excel workbooks. The platform replaces those workbooks first, then grows into the department’s management system.

**Organization.** Smart Factory Manager → Digital Systems Manager (sections Design & Project, Development, Implementation & Support) and Sr. Equipment Development Engineer (section Equipment & Automation). 16 positions, about 50 people per the table of organization, several positions vacant or new. The two groups inside Digital Systems (Customer, Enterprise) are assignments, not positions.

**Why it is being replaced.** Weekly consolidation is manual (open, copy, Paste Values per person), definitions exist in two places, month status is only known after consolidation, and remarks live in a log read back by lookup. **Management direction that shaped the measures.** Reduce manual processes, consolidate the systems used on the line, cut paper, improve efficiency; projects are initiatives, outcomes are the KPIs.

## Domain model

The model is the Excel system made explicit: one KRA per person per half-year, made of up to 20 slots; results are stored per slot per work week; everything else is derived.

| Entity | Key fields | Notes |
| --- | --- | --- |
| Department / Section / Position | name, parent, reports-to position, headcount per T.O. | Section carries the category ownership used by the Scores (section 6) |
| Person | employee id (from LDAP API), name, position, section, assignment (Customer / Enterprise), start date, active | A position may have many incumbents; vacancies are positions without a person |
| Fiscal period | FY (Apr–Mar), half (1H/2H), month | 2H FY2026 = Oct 2026 – Mar 2027 |
| Work week | label (WW40), ISO week, start Monday, end Sunday, assigned month, k = week in month, n = weeks in month | Rule in 5.1; generated, not typed |
| Top Goal line | focus item, strategic objective, Top Goals measure | 16 company lines (section 6); the dropdown every slot must pick from |
| Rating basis | key, name, mode (RH / RL / AL / M), t5, t4, t3, t2, band texts, notes | Editable library (section 6); referenced by key |
| KRA | person, half-year, version, mode (SETUP / LOCKED), approved by, approval date | One active version per person per half; history kept |
| KRA slot | KRA, slot number 1–20, Top Goal line, measure, target text, weight, rating basis, aggregation (LAST / SUM / AVE / MANUAL), weekly target rule (RAMP / PRORATE / ZERO / FLAT / MANUAL), start value, plan per month (6), notes | Active when measure is non-empty; weights of active slots must total 100% |
| Weekly result | slot, work week, actual (number), manual weekly target | Actual is typed in module 1; later fed by Registers |
| Monthly manual value | slot, month, manual actual, manual rating | Only read when aggregation = MANUAL or basis mode = M |
| Remark | slot, period (work week or month), author, text, created at | Shown on dashboards for the slot and period |
| Derived (never stored as truth) | weekly target, monthly actual, monthly rating, weighted score, monthly total, 2H rating, weekly rating, week judgement, month status | Computed from the rules in section 5; may be cached |

Relationships: Person → one KRA per half-year; KRA → up to 20 slots; slot → one weekly result per work week and one manual value per month; slot → many remarks. Section-level and department-level measures are ordinary slots on the head’s or manager’s own KRA; the cascade is expressed by the Top Goal line each slot points to and by who owns it, not by linking slots to each other.

Requirement sub-items (the register that will later drive % closure and the two Scores) belong to the reserved Registers module; module 1 only stores the typed weekly percentage.

## Business rules (exact)

Every rule below is implemented and verified in the Excel system; implement it as written and cover it with the tests in section 11.

**5.1 Calendar.** Work weeks are ISO weeks, Monday to Sunday, labelled WWnn by ISO week number. A week belongs to the month that holds more of its days, which for a 7-day week is the month of its Thursday. For 2H FY2026 that gives WW40 (28 Sep – 4 Oct 2026) through WW12 (22 – 28 Mar 2027): Oct 5 weeks, Nov 4, Dec 5, Jan 4, Feb 4, Mar 4; 29–31 March fall in WW13 (April) and are outside the half. For each week store k (week number within its month, from 1) and n (weeks in that month).

**5.2 Weekly target** for a slot in week (m, k, n), with plan Pₘ for month m and Pₘ₋₁ the previous month’s plan (for the first month, the slot’s start value; blank counts as 0):

```latex
\begin{aligned}
\text{RAMP:}\quad & T_w = P_{m-1} + (P_m - P_{m-1})\cdot\tfrac{k}{n} \\
\text{PRORATE:}\quad & T_w = P_m / n \\
\text{ZERO:}\quad & T_w = 0 \\
\text{FLAT:}\quad & T_w = P_m \\
\text{MANUAL:}\quad & T_w = \text{typed weekly target}
\end{aligned}
```

If the slot’s aggregation is MANUAL, or Pₘ is blank, the weekly target is blank.

**5.3 Monthly actual** from the weekly actuals Aᵢ entered for weeks of month m (blank weeks ignored):

| Aggregation | Monthly actual |
| --- | --- |
| LAST | the actual of the latest week (highest k) that has a value |
| SUM | Σ Aᵢ |
| AVE | Σ Aᵢ ÷ count of weeks with a value |
| MANUAL | the typed monthly manual actual; weekly cells unused |

No weekly value and nothing manual → blank.

**5.4 Rating** of an actual A against a target T under a rating basis (mode, t5, t4, t3, t2):

```latex
\begin{aligned}
\text{RH } (r = A/T):\quad & 5 \text{ if } r > t_5;\ 4 \text{ if } r \ge t_4;\ 3 \text{ if } r \ge t_3;\ 2 \text{ if } r \ge t_2;\ \text{else } 1 \\
\text{RL } (r = A/T):\quad & 5 \text{ if } r < t_5;\ 4 \text{ if } r < t_4;\ 3 \text{ if } r \le t_3;\ 2 \text{ if } r \le t_2;\ \text{else } 1 \\
\text{AL:}\quad & 5 \text{ if } A \le t_5;\ 4 \text{ if } A \le t_4;\ 3 \text{ if } A \le t_3;\ 2 \text{ if } A \le t_2;\ \text{else } 1 \\
\text{M:}\quad & \text{the typed manual rating 1–5}
\end{aligned}
```

RH and RL are blank when A or T is blank or T = 0; AL is blank only when A is blank. Thresholds of 9 (RH / RL) or −1 (AL) make a band unreachable, which is how “no 4 or 3” shapes are built. The same function rates a month (monthly actual vs. plan) and a week (weekly actual vs. weekly target).

**5.5 Scores.** Weighted score = rating × weight. Monthly total = Σ weighted scores of active slots (complete only when every active slot has a rating that month). 2H rating per slot = average of the monthly ratings that exist; 2H performance = Σ (weight × 2H rating per slot). 3.00 means every target met; 5.00 is the ceiling. Ratings below 3 are highlighted red.

**5.6 Week judgement** (dashboard, weekly): Met if A ≥ T for RH, Met if A ≤ T for RL and AL, else Unmet; blank if either value is missing or mode is M.

**5.7 Month status** (Met / Unmet / —). Let *final* be true when the month is complete: in the weekly view, the previous work week is the last week of its month; in the monthly view, the month’s last week has an actual, or the slot is MANUAL and has a monthly actual. Then:

- mode M → no status; A or T blank → —
- RH: Met if A ≥ T and (final or aggregation ≠ AVE); else Unmet if final; else —
- RL / AL: if A > T then Unmet if (final or aggregation = SUM), else —; if A ≤ T then Met if final, else —

The intent: conclude early only when the outcome cannot change – a cumulative target already reached, a summed zero target already broken. Averages and month-end snapshot counts (overdue open issues, projects behind target) can still move, so they wait for month end. Colours: Met green, Unmet red, — amber.

**5.8 KRA Setup rules.** A slot is active when its measure is non-empty. Active weights must total 100% before the KRA can be locked. Mode SETUP allows edits; LOCKED rejects edits to definitions (measure, target, weight, basis, aggregation, rule, plans, start value) and records approver, date and a new version on each lock. Changing a locked KRA requires unlocking, which creates a new version; weekly results stay attached to the slot number. Top Goal line is mandatory and must come from the 16 company lines.

**5.9 Guardrails from the design** (enforce in the module, not only in guidance): sub-items committed for a month are locked at month start, removal needs documented approval by the section head, and an item dropped without approval counts as not closed; projects are initiatives, never % complete KPIs; no slot may measure a result its owner cannot influence (the Top Goal line plus the position decides this); the Rating basis library is the only place rating bands are defined.

## Roles, permissions and workflows

The consolidation step disappears: each person works on their own KRA in the platform and their superior sees it live. Permissions follow the reporting line in the Organization service.

| Role | May do | May not do |
| --- | --- | --- |
| Person (any incumbent) | Edit own KRA in SETUP; enter own weekly actuals, manual values, remarks; view own dashboards | Change own KRA while LOCKED; see other people’s KRAs |
| Section head | Everything a person can for own KRA; view all KRAs and results in the section; approve and lock / unlock subordinates’ KRAs; write remarks on any slot in the section; team view | Edit a subordinate’s definitions directly (ask them to change in SETUP, then approve) |
| Manager (Digital Systems Manager, Smart Factory Manager) | View every KRA and result beneath them; approve and lock section heads’ KRAs; department and section dashboards; trigger exports | Edit anyone’s definitions directly |
| HR viewer | Read the half-year export for all people | Anything else |
| Administrator | Organization data, periods, rating basis library, Top Goal lines, role assignment | Enter results on anyone’s behalf except by import |

**Workflows**

1. **KRA setup and approval.** Person fills slots in SETUP → weight check must read 100% → person submits → superior reviews the slots against the Top Goal lines and the position → approve (LOCKED, approver and date recorded, version +1) or return with comments. A KRA with no version locked by the end of the first week of the half is flagged on the superior’s dashboard.
2. **Weekly entry.** By Friday each person enters the week’s actual per active slot (the register-fed version replaces this step later). The week’s judgement and the running month status update immediately; the superior sees the team view on Monday and writes remarks on the week.
3. **Monthly close.** When a month’s last week has actuals for every active slot, the monthly rating, weighted scores and total become final; a month with any slot still blank shows the total as provisional.
4. **Half-year export.** At the end of 2H, export every person’s KRA on the company Target Indices form (Excel, same layout as the definitions workbook: focus item, objective, measure, departmental and sectional goals / measures, target, weight, monthly ratings, scores, rating reference) for HR submission; one file per person plus one consolidated file.
5. **Change requests mid-half.** Unlock → edit in SETUP → re-approve; the change trail records old and new values, who and when. Guidance shown in the UI: prefer changing target or rating basis; to change a measure’s meaning, retire the slot and open a new one so weekly history stays truthful.
6. **Vacancy and joiners.** A new incumbent inherits the position’s template slots as a SETUP draft; a leaver’s KRA is frozen with its results.

## User experience direction

## Non-functional requirements and environment constraints

The platform runs on the FSCI LAN with no internet access, under company IT policy; every development session must respect these before choosing a stack.

- **Language and database** are mandated by company policy; confirm the mandated choices at the start of a session and do not substitute. Dependencies must be installable offline from an internal mirror.
- **Source control:** the local GitLab server, following the company folder convention.
- **Identity:** sign-in and employee data only through the company LDAP / employee-info APIs; never a direct LDAP bind.
- **Email:** only through the company Exchange API (a single permitted server address).
- **Fonts and assets:** bundled locally; no calls to external CDNs or Google Fonts at runtime.
- **Scale:** about 60 users, 16 positions, 20 slots × 26 weeks per person per half; a few hundred thousand rows per year. Correctness and auditability matter more than throughput.
- **Audit trail:** every change to a KRA definition, approval, lock, weekly result or remark records who, when, old and new value.
- **Availability:** business hours; nightly backup; restore tested before go-live.
- **Exports:** Excel on the company Target Indices form; the export must round-trip the definitions workbook layout exactly so HR receives what it receives today.
- **Accessibility and devices:** keyboard-operable, colour never the only signal (Met / — / Unmet carry text), usable on a phone for weekly entry and the Ascent view.
- **Localisation:** English UI; dates shown as dd Mmm yyyy; fiscal labels (2H FY2026) beside calendar months.

## Open decisions, assumptions, and how to prompt new sessions

**Open decisions (answer before or during the first sprint)**

- [ ] Product name: “Smart Factory Platform” is a placeholder; the mockup used “Ascent” for the home screen only.
- [ ] Mandated language, framework and database under FSCI policy, and the internal package mirror.
- [ ] E&A abnormality bands: zero\_diff (0 = 5, 1 = 2, 2 or more = 1) or zero\_diff2 (1–2 = 2).
- [ ] I&S SLA target 90% from October, or a ramp (70 / 80 / 90) given the 57% baseline in the working file.
- [ ] Whether month-end snapshot counts (overdue open issues, projects behind target) may conclude Unmet before month end; currently they wait.
- [ ] Section sub-targets for the Scores once a deployment plan with station counts exists (replaces the interim company-ramp assumption).
- [ ] Who may unlock a LOCKED KRA mid-half: the superior only, or also the person with superior re-approval.
- [ ] Register-fed actuals: which register goes native first (recommendation: the sub-item register, because it moves the Scores and every person’s % closure).

**Assumptions carried from the Excel system**

- One active KRA per person per half; history is versions, not duplicates.
- Personal, section and manager results never roll up arithmetically; each level reads the same registers at its own scope. The team view is diagnostic, not an input to anyone’s rating.
- Project Completion Rate carries weight 0 everywhere in Smart Factory (delivery is measured through sub-items); Reduction of manual process is owned by Process Engineering; T.O. fill and key-personnel retention are manager measures only.
- The plant-wide outage threshold is 30 minutes; the isolated downtime allowance is 120 minutes per month.

**Prompting guide for a new development session**

1. Start the session with sections 1, 3, 4 and 5 verbatim, then the constraints in section 10, then the acceptance tests in section 11. Attach the definitions workbook and \_builders/ when the session will seed data.
2. Ask for the build in this order: core (organization, periods, identity, audit) → module 1 data model and rule engine with the 22 tests green → import from the Excel assets → screens in the order of the table in section 9 → export → parallel-run reconciliation.
3. Tell the session what not to do: no scorecard assumptions in the core; no external CDNs or fonts; no direct LDAP; no change to a rule in section 5 without updating section 11; no “project % complete” measures.
4. When the session proposes a deviation, have it write the change as a numbered rule change with the test it alters, so this document stays the contract.
5. For module 2 (Registers), reopen section 8 and promote the chosen register from import to native; the weekly result `source` field already supports it.
